## Supported starting point

- A fresh store, or content already at the 2026-10-20 shapes, may start without a ledger. Choosing
  migrations for that store accepts this baseline; the runner does not infer content age.
- An existing flat ledger must have `schemaVersion: 18`, eighteen ordered entries for versions
  1–18, matching script/version numbers, and terminal script `V018__drop-scroll-offsets.js`.
  It must belong to this store. Missing/truncated/ambiguous histories or any other version fail.
- A format-2 ledger resumes by source ID and must match the delivered baselines. Different
  checkout/install paths do not change identity. A copied or moved **store** needs an explicit
  `dataRoot` relocation; this is distinct from relocating source scripts.

The compact base ledger is:

```json
{
  "formatVersion": 2,
  "dataRoot": "/absolute/store",
  "sources": {
    "kiao": {"baseline":18,"schemaVersion":18,"applied":[]}
  }
}
```

Additional sources start with their own baseline and empty applied list. The first future base
script is V019; a new extension may use V001. Removed versions never become available for reuse
under the same ID. Ordinary applied migrations remain immutable; this dated, checked retirement is
the coordinated exception, not a routine reset procedure.

## Older stores

Do not remove their ledger or declare baseline 18 to bypass a failure. Recover a pre-cutover checkout
from Git (the parent of the retirement change in that repository contains the complete inventory).
Keep its worker, helpers and eighteen scripts together. Rehearse its normal runner on a copy with
the store's real `.kiao-files` declarations, inspect skipped/unresolved documents and the diff,
then run it against the stopped original with its original ledger. Confirm version 18 and the
terminal script before installing this release. Preserve intentional exclusions; a migration being
recorded does not assert that an excluded file was converted.

A ledger from the earlier, already-retired pre-V001 lineage cannot be identified by a version
number alone. An old `<store>/.kiao/migrations.json` is retained; with no current ledger it blocks
automatic baseline adoption, including after a startup with migrations disabled. Restore its
matching release/ledger from backup or Git and follow that release's
upgrade procedure on a copy first. Do not apply this retirement's flat-ledger transition to it.
Where provenance cannot be established, make a deliberate, reviewed content conversion into a
fresh current store; automatic upgrades from unknown old shapes are unsupported.

## Delivery procedure

1. Inventory each store's ledger and each configured script directory, including remote staging
   and installed copies. Back up the store/state and the matching binary, scripts and config
   outside every mirrored/deleted delivery directory. Keep backups private.
2. Build using the repository's shared build stage and target installer. Stage into an empty set
   with `bin/stage-file-migrations.js`; validate the assembly has only scripts above each baseline.
3. Copy a real store and its state. Set the copy's ledger `dataRoot` to its new absolute path.
   In a copied delivery, plant an old script, replace the complete migration set with the staged
   one and confirm that script disappeared. A surviving retired script must abort before the
   original ledger is compacted.
4. Run the delivered binary against the copy, twice:

   ```sh
   KIAO_WORKER_AUTH_MODE=debug KIAO_WORKER_ROOT_PATH=/absolute/copied-store \
   KIAO_WORKER_MIGRATIONS_SOURCES=/absolute/copied-delivery/migrations/sources.json \
   /absolute/copied-delivery/worker migrate-files
   ```

   Leave `KIAO_WORKER_STATE_PATH` unset so this uses the copy's state. Verify the format-2
   baseline, empty retired histories, byte-identical content and an identical ledger on restart.
   Add fixture-only post-baseline scripts to the **copied delivery**, run twice, add a later base
   version, and verify each successful script is recorded once. Never deploy these probes.
5. Stop the current service. Replace every active migration directory in full; do not overlay.
   The executable installer removes `<install>/migrations`, Docker builds a clean image, and a
   server install must replace both its remote staging set and installed set. Do not bind an old
   host migration directory over the new image's set.
6. Start the new worker with the target's existing enablement policy. Confirm source IDs,
   baselines, script counts and ledger compaction; check readiness, restart and recheck. With
   migrations disabled, ledger conversion remains deferred until explicit opt-in.

At this cutover there are **zero active content scripts**. A conversion runs no content migration;
it replaces eighteen applied entries with the base baseline and initializes configured additions.
The flat ledger is compacted only once; a format-2 restart never repeats that transition.

For rollback, stop the worker and restore the **matching** old binary, script set and backed-up
ledger together. An old worker cannot interpret format 2 and would otherwise treat its scripts as
pending. If any post-cutover content migration ran, restore the matching content snapshot too.
Keep old executables/images out of automatic startup. Never mix a compacted ledger with an old
runner or a fresh ledger with the retired scripts.
