# Build, run and code map

← [worker](/operation/worker/README.md) · assumes the index.

## Build & run

```bash
# Production binary (linux/amd64, static):
./build.sh                 # -> ./worker

# Run locally in debug mode (no auth), from the project root:
./bin/local-start-kiao.sh  # kiao: this service + Dashboard, store root picked from a menu

# Tests:
go test ./...
```

Requires Go 1.24+.

## Code map

> Adding an endpoint? Step-by-step checklist: [`ADDING-AN-ENDPOINT.md`](/operation/worker/ADDING-AN-ENDPOINT.md).

**Four libraries, one program.** No network boundary between them, one binary, one process.

```
main.go, server.go, state_legacy.go   the program — startup, the mux, and nothing else
internal/core                         the socle — store access, access control, configuration, log
internal/files                        the document store — browse, search, Git, links, actions, migrations
internal/hybridflow-runner            the hybridflow runner — conversations, turns, quota,
                                      permissions, skills, attachments, the board
internal/toolbox                      the outfitting of the machine — what is installed on it, and
                                      which MCP servers a turn is handed
```

Each depends on `core` and **never on the others**. The program is the only place that knows them
all: it loads the configuration, hands each library its share, mounts their routes on one mux, and
fills the ports that join them. The boards live in the hybridflow-store and are reached over HTTP, so
this half takes no port into the file service. `hybridflowrunner.MCPRegistry` is the toolbox, asked
at every turn spawn which MCP servers that turn should get. `main.go` also hands the toolbox what the
staged kiao-mcp bundle offers (`hybridflowrunner.BundledMCPServers`), because that bundle's path is the hybridflow-runner
half's configuration and the switch that turns its servers on and off is the toolbox's. The document
store is handed where ffmpeg is the same way — `toolbox.RuntimeBinary("ffmpeg")` through
`files.UseFFmpeg`, asked at every save of a video's segments, so installing it from the
Configuration panel takes effect on the next click.

The single genuine coupling is the **turn token** (`core/turntoken.go`). A turn is a CLI process this
service spawns, whose MCP servers call this service back to read and write documents; the hybridflow-runner
half mints the credential and the access-control half has to honour it. Both live in the socle,
which is what keeps the loop from being drawn between the two libraries.

What each `.go` file owns:

**The program**

- `main.go` — process entry point: load and validate config (fail-fast, one list across all four), log the resolved config, create and lock the state directory (fail-fast), seed and log the store declaration, adopt state from the previous layout, run pending migrations (fail-fast), start each library, wire the turn tokens into the authenticator, start the HTTP server.
- `server.go` — `Server`, `routes()` (each half's table, concatenated), `handler()` (the mux plus the recover → CORS → request-id → trace → auth chain), `readerRoutes` (the read-only surface, spelled as the route tables spell it), the unauthenticated `/healthz` probe.
- `state_legacy.go` — one-time adoption of the registries and config documents a store written by the previous layout still keeps in the data root. The one pass that has to name both halves' files, which is why it is here.

**The socle (`internal/core`)**

- `core/config.go` — the `Config` every library embeds (port, store root, state path, issuer/JWKS, reader roots, node binary, auth mode) plus the `Getenv*` helpers each half reads its own settings with.
- `core/http.go` — the middleware chain (`RecoverMiddleware`, `CORSMiddleware`, `WithRequestID`, `TraceMiddleware`), `statusWriter`, the JSON/text response helpers, and `Route`, which is how a library states its HTTP surface as data.
- `core/log.go` — `log/slog` text logger: one process logger, `Component` for the per-subsystem `component=` loggers each half declares, and request-id helpers (`WithRequestID` writes a short id into the context and `X-Request-Id`; `RequestID`/`LogCtx` read it back). Lines go to stdout, captured by journald under systemd.
- `core/errors.go` — the error taxonomy: `ClientError` and `Invalid`, with which each half declares its own caller-mistake sentinels, the explicit `HTTPError`, and `StatusForError` / `WriteError` that classify a handler's error into an HTTP status (see [Error taxonomy](/operation/worker/README.md#error-taxonomy)). Keeps handlers from choosing status codes by hand.
- `core/state.go` — filesystem helpers for the service's *own* state, deliberately outside `Storage` (whose job is bounding paths a client may browse): `WriteFileAtomic` (temp + fsync + rename, the replace every registry writes through), `EnsureStateDir` and the `.gitignore` that keeps state out of the Source Control panel.
- `core/turntoken.go` — `TurnTokenRegistry`: the credential this service issues to the turns it spawns, so their MCP servers can call back in. Minted by the hybridflow-runner half, honoured by the authenticator, and destroyed when the turn ends.
- `core/ids.go` — `RandID` and `NowMillisStr`, the two halves every id this service mints is made of.

**File store**

- `files/handlers_files.go` — HTTP handlers for the file endpoints (`/getFile`, `/upload`, `/update`, `/delete`, `/list`, `/listRecursive`, `/info`, `/createFolder`, `/rename`, `/moveBatch`, `/copyBatch`, `/search`, `/reindex`, `/diskUsage`). `/getFile` hands a regular file to `http.ServeContent`, which is where ranged and conditional downloads come from.
- `files/service.go` — `FileService`, the file application layer wiring storage to the subsidiary, index and link-fix helpers.
- `files/optimize.go` — what the store is carrying that it need not be: one walk answering both the files stored more than once (grouped by size, then hashed) and the biggest ones, plus the consolidation that reduces a set of identical files to one — expressed as a move onto the survivor, so the link fixer repairs every reference to the copies that go.
- `core/storage.go` — `Storage`, the OS-filesystem driver; every path is relative to the root, bounds-checked, and refused when it lands in the state directory sitting inside that root.
- `core/path.go` — `core.ResolvePath`: joins a subpath onto the root and rejects traversal that escapes it.
- `files/dto.go` — the JSON DTOs of the store, whose field names *are* the wire: `FileDto`, `FileCompanionDto`, `DiskUsageDto` and the rest of the Java-parity set (mirrored in `reference/npm/kiao-worker`, described in [PROTOCOL.md](/operation/worker/PROTOCOL.md)). The Claude ones are `hybridflow-runner/dto.go`, bound by the same rule.
- `files/config.go` — the settings this half reads on top of the socle's: git identity, link-fix extensions and workers, the migration runner, the action manifest.
- `files/routes.go` — this half's HTTP surface, as data.
- `files/api.go` — `files.Service`: what the program mounts.
- `files/staging.go` — the **staging area**: the directory an upload lands in before anybody has said what to keep (`.kiao-uploads/u-<clock>-<rand>`, one per upload), and the two endpoints that open and discard one. It reimplements nothing — a staging area is an ordinary directory, so `/upload`, `/reindex`, `/moveBatch` and `/delete` work on it as they do anywhere, importing *is* a moveBatch out of it and deleting *is* the area going away. What is here is the three things an ordinary directory could not be: hidden from listings (`core.Storage.IsStagingRoot`), kept out of git by a seeded `.gitignore` of `*`, and swept of the areas an upload never came back to answer for. The recursive discard is bounded to what this file minted (`ErrNotStaging`), which is what lets it run with no confirmation in front of it.
- `files/importgate.go` — the **import gate's catalogue**: the JSON in `importgate/`, embedded, and the one call that writes it into a store with no `kiao-user-config/import-gate/`. Nothing here runs a matcher — the gate is a regular expression Dashboard applies in the browser to the text of a document it is reviewing, and this half only makes sure a store that nobody has configured has a usable one. Seeded whole and once: the folder is the store's from the moment it exists, so a category somebody deleted does not come back at the next restart.
- `files/pdfthemes.go` — synchronizes the bundled `pdfthemes/` files to `kiao-user-config/pdf-themes/` at startup. Delivered filenames follow the build; custom themes keep their own filenames. Dashboard reads these JSON documents for its Markdown PDF menu and print styles. The [theme README](../internal/files/pdfthemes/README.md) describes customization and synchronization.
- `files/subsidiary.go` — companion-file family: recognises known subsidiary suffixes (a `<main><suffix>` file belongs to `<main>`).
- `files/fileindex.go` — file-index helpers; **converts** a document into a sibling index so search scans text, not the binary — and so a person can open what it says. The `extractors` table (extension → converter *and* the format it writes) is the single list of indexable types and drives `createIndex`, `/reindex` and search's refresh pass alike: `.pdf`, `.docx`, `.pptx`, `.odt`, `.eml` and `.msg` become `<name>.index.md`; `.xlsx`, `.xlsm` and `.ods` become `<name>.index.csv`; `.index.txt` stays a recognised index, as the format older versions wrote and as one a person may write by hand. `stateOfIndex` is the rule that decides what may be rewritten: a generated index carries its source's mtime, so an index *newer* than its source is one somebody wrote, and nothing automatic ever touches it.
- `files/fileindex_markdown.go` — the sink every converter writes into (`textBudget`, and the `maxIndexTextBytes` ceiling that truncates rather than fails) and the Markdown and CSV vocabulary it offers: headings, bullets, pipe rows, RFC 4180 fields.
- `files/fileindex_ooxml.go` — the zip+XML conversion engine shared by the OOXML and OpenDocument families (`xmlTextRules` and its `classify` hook, the table triple, the zip-entry helpers), plus the `.docx`, `.pptx` and `.odt` converters. Word headings come from `w:outlineLvl` first and the style name second, because the built-in style names are localised. Standard library only, so the binary stays static and the host needs no converter installed.
- `files/fileindex_xlsx.go` — spreadsheet conversion (`.xlsx`/`.xlsm` and `.ods`), which needs its own parser for the shared-strings indirection and the OpenDocument repeat counts. Emits one CSV record per row so a search hit shows the whole record.
- `files/fileindex_pdf.go` — PDF text, one `## Page n` section per page. The only format needing a third-party parser (`github.com/ledongthuc/pdf`, pure Go): a page is positioned glyphs against a font encoding, and the page number is the only landmark extracted PDF text has.
- `files/fileindex_mail.go` — the `mailDocument` both mail formats produce and the Markdown it renders as (subject as the title, a header block, the body, then the attachments *named* and not opened), plus the `.eml` reader: MIME walk, transfer encodings, RFC 2047 headers, and the charset fallback that reads non-UTF-8 bytes as Windows-1252.
- `files/fileindex_html.go` — HTML reduced to the text it displays, for the mail bodies that come only as HTML. A scanner, not a parser: what an index needs is where the breaks go and which subtrees are not text.
- `files/fileindex_msg.go` — Outlook `.msg`: the MAPI property model (`__substg1.0_<tag>` streams, attachment sub-storages, the fixed property stream holding the times) read into the same `mailDocument` as an `.eml`, so both index alike.
- `files/fileindex_cfb.go` — the Compound File Binary (OLE2) container a `.msg` is: sector geometry, FAT and mini FAT, and the directory tree. Written here rather than taken from a library, for the same reason the OOXML engine is.
- `files/linkfix.go` — `LinkFixer`: rewrites markdown/text link references after a rename or delete (RE2, with manual boundary checks). **A link is a path written from the store root, with a leading slash**, and nothing without one is matched: a store's root folders are ordinary words, so a bare `config/values` is a shell snippet as often as it is a reference, and a path written without the slash is a document-relative markdown link pointing somewhere else. A link is matched both verbatim and percent-encoded — a stored one keeps whatever escaping it was written with, so `/docs/🎓/Board` and `/docs/%F0%9F%8E%93/Board` are the same link — and the new path is written back in the form the link it replaces used. Reading and writing take **different** escape sets on purpose: a match accepts both spellings of anything outside RFC 3986's unreserved set, because nothing says the reference was written by this application, while what the fixer writes is Dashboard's own rule (`storedLinkOf`), so a repaired link reads as the link the application would have written.
- `core/diskusage_linux.go` / `core/diskusage_other.go` — `Storage.DiskUsage`, per platform (statfs on Linux, zeroes elsewhere).

**File actions**

- `files/actions.go` — `ActionCatalog`: manifest loading and validation, the applicability rule (`actionApplies`), and the provider call. Knows nothing of any individual action.
- `files/media.go` — a video's segments saved as files of their own, AV1 and Opus in Matroska: the refusals made before anything runs (a name that is not a file, two segments on one file, one on the source itself), the two quick questions asked of ffmpeg (which encoders it has, which streams the source holds), the command line that cuts to the image, the hidden name renamed over the destination so a file is replaced whole, and the one save slot a client polls. ffmpeg is wherever `UseFFmpeg` says — the toolbox's `RuntimeBinary("ffmpeg")`, asked at every save. `files/handlers_media.go` is its HTTP surface.
- `files/handlers_actions.go` — HTTP handlers for `GET /actions` and `POST /actions/run`.

**Git (Source Control)**

- `files/handlers_git.go` — HTTP handlers for the `/git/*` endpoints.
- `files/git.go` — `GitService`: runs `git` with explicit argument lists (never a shell) against the root working tree.

**Claude**

- `hybridflow-runner/driver.go` — the seam between this half and the agent behind it. `AgentDriver` is one turn in five verbs — `Spawn`, `Events`, `Answer`, `Say` (what a `between` is), `Stop` — with `AgentRun` going in and a stream of `AgentEvent` (a block, an ask, the session, the end) coming back. Five optional side ports — `AgentOptions`, `AgentUsage`, `AgentLogin`, `AgentMCP`, `AgentBranching` — are what the quota, the prompt's choices, the sign-in panel, the MCP configuration and the meaning of a fork hang off: an agent that answers none of them leaves those routes unmounted, so the panel *disappears* rather than failing on an endpoint that cannot work.
- `hybridflow-runner/driver_claude.go` — the `claude` CLI behind that port, and the only file that knows it exists. `claudeAgent` makes a driver per turn and answers every side port; `claudeDriver` is one turn's process, its stdin and the goroutine that turns its stream-json into `AgentEvent`s. `claudeArgs` is the single place the CLI's argument list is built, and `agentBriefing` (`hybridflow-runner/briefing.go`, shared with the Codex driver because it describes the *surface* and not the agent) is what the model is told about where its reply lands: Dashboard renders it with the store's own markdown renderer, so a fenced `mermaid` / `plantuml` / `archdia` / `graph` / `svg` block is drawn as a diagram and a destination like `/units/abc/cadre.md` is a link that opens the file in the CMS. Neither is discoverable from inside a turn, and both fail silently — the diagram comes back as source, the path as prose. It rides `--append-system-prompt` rather than the prompt text, so it is stated once per turn instead of once per message and stays out of the transcript, and it names this deployment's store root so an absolute path can be converted into a link.
- `hybridflow-runner/driver_codex.go` — `codex exec --json` behind that port, and the only file that knows *that* CLI exists. One process per turn, JSONL thread events in (`thread.started`, `item.completed`, `turn.failed`), `AgentEvent`s out: a message is text, reasoning is thinking, and `command_execution` / `file_change` / `mcp_tool_call` / `web_search` / `todo_list` are tool calls under the CLI's own names. Two of the five verbs answer errors rather than pretending — `codex exec` never asks, so nothing is ever answered, and its stdin carries the prompt and is closed, so nothing can be said into a running turn. The briefing travels on `developer_instructions`, which is this CLI's `--append-system-prompt`; `model_instructions_file` would *replace* the model's instructions rather than add to them.
- `hybridflow-runner/codex_options.go` — what the prompt offers for Codex: the models and reasoning levels read from `codex debug models`, and `bypassPermissions` as the one permission mode there is. A catalogue that cannot be read leaves both lists empty rather than guessing — there is no equivalent of the stable Claude aliases to fall back on.
- `hybridflow-runner/codex_mcp.go` — the second rendering of the one ledger: the whole `mcp_servers` table as a TOML inline table on a `-c` override, Codex having no `--mcp-config`. It is also where the one real cost of this driver is written down. Codex neither expands `${VAR}` in a configuration value nor passes its own environment to a stdio MCP server (measured, not assumed — not even with `shell_environment_policy.inherit = "all"`), so a per-turn credential can only reach a server by being written into the configuration; and since `codex exec resume` takes no `--profile`, that configuration is the command line. The token is therefore visible in `ps` for the life of the turn, which is why it is minted per turn and revoked when the turn settles.
- `hybridflow-runner/driver_opencode.go` — `opencode run --format json` behind that port, and the only file that knows *that* CLI exists. One process per turn, run events in (`text`, `reasoning`, `tool_use`, `step_finish`, `error` — each carrying the session id), `AgentEvent`s out: a text is text, a reasoning is thinking, a tool_use is a tool call with its outcome on it, and the steps' tokens fold into the turn's one bill. Two of the five verbs answer errors rather than pretending — without `--auto` a permission request is auto-rejected, so nothing is ever answered, and stdin carries the prompt and is closed, so nothing can be said into a running turn. The briefing travels in the input text ahead of the prompt, the CLI having no per-turn system prompt; sessions resume with `--session` and fork with `--fork`.
- `hybridflow-runner/opencode_options.go` — what the prompt offers for OpenCode: DeepSeek V4 Pro and Mistral Large 4 first, then whatever `opencode models` reports for the providers this host configured; the `low` / `medium` / `high` / `max` variants DeepSeek V4 carries, passed as `--variant` and ignored by a model carrying none; and `bypassPermissions` as the one permission mode there is. A catalogue that cannot be read leaves the curated two alone rather than guessing — they are verified ids, and an empty list would make the two models this agent exists to run unnameable on exactly the host being set up.
- `hybridflow-runner/opencode_mcp.go` — the fourth rendering of the one ledger: the `mcp` object of a config document carried in `OPENCODE_CONFIG_CONTENT`, which the CLI merges over every other source. The ledger's `${VAR}` becomes the `{env:VAR}` the CLI expands from the turn's own environment, so the credential is never written to a file and never appears in `ps` — the Claude arrangement, in OpenCode's spelling.
- `hybridflow-runner/agent_process_linux.go` — the per-turn Codex subprocess supervisor: a Linux subreaper with a worker-owned control pipe. Launcher exit, cancellation and worker death kill and reap all local descendants, including tools that leave the initial process group. Its private worker entry point runs before server startup.
- `hybridflow-runner/agents.go` — which agents this deployment offers, which is the default, and the three questions asked of one: does it publish this permission mode, can it branch a session, and what does a conversation on it start with. A conversation is bound to its agent at creation like its folder, and for a stronger reason — a session id belongs to one engine, so changing agent is a fork rather than a patch.
- `hybridflow-runner/briefing.go` — what the model is told about the surface its reply lands on, above the port because it is true of the surface and not of the agent. Only the way it travels is each driver's business.
- `hybridflow-runner/claude_ws.go` — `ClaudeHub` backing `/ws/hybridflow-runner`: owns the turns, and **knows no agent**. It spawns one driver per turn in the conversation's folder, drains its events onto the socket, relays and answers the asks it parks on, and records each turn's two transcript boundaries. The parallelism cap, the job TTL and the turn registry are here too.
- `hybridflow-runner/claude_ws_fanout.go` — the routing half of the hub: the subscription map, `emit` / `emitFor` / `emitTo` / `fanout` / `broadcastRegistry`, and the three frame classes that decide which of those a frame goes through. `errorFrame` and its `code` vocabulary live here.
- `hybridflow-runner/claude_ws_conn.go` — `wsConn`: one browser socket, with serialised bounded writes, an idempotent close, a read limit and the ping/pong heartbeat. Everything in it exists because the socket is now open for as long as the tab is, instead of dying with the turn it carried.
- `hybridflow-runner/claude_folder.go` — `resolveClaudeFolder`, which validates the folder a turn runs in. Stricter than `core.ResolvePath` because the result becomes a process's working directory: symlinks are followed and the result re-checked against the store root. Also `folderLabel`, how a virtual path reads in a sentence.
- `hybridflow-runner/conversations.go` — `ConversationStore`: one directory per conversation (`meta.json` + append-only `transcript.jsonl`), id minting and shape validation, transcript compaction, title derivation, and `sweepInterrupted` for turns a restart killed.
- `hybridflow-runner/turn_trace.go` — the per-turn trace under `<conversation>/turns/<turn id>.jsonl`: how the process was actually run (argv, the binary and its version, what this service added to the environment, the pid, the skills, the configuration staged and then deleted), every line the agent wrote to stderr, and — switched per conversation with `traceStream` — the raw protocol in both directions. The operational half of a turn, kept out of a transcript that is read as a conversation. Bounded three ways (one trace, one record, traces per conversation), scrubbed of the turn's credential whatever shape it arrives in, and never a reason for a turn to fail: a trace that cannot be opened is one warning and a nil handle every method is safe on.
- `hybridflow-runner/chain_run.go` — `ChainRunner`: the chain runs a service has under way. Plays a flow node, waits for its turn, files the answer, follows the chain, waits out the errors worth waiting out — a usage limit on the clock its own notice names, and by resuming the cut-off turn rather than sending the flow node again — and tells every socket where it stands.
- `hybridflow-runner/chain_run_log.go` — the per-run log under `<state>/chain-runs/<run id>/`: a `meta.json` saying what the run is, and an append-only `run.jsonl` of what it decided — every notice it raised, every move it made, every turn answered (what it was sent as, what it ran on, the refusal or fault it came back with), every handoff (what the finished card says, the folders on both sides, the branch taken) and every wait. The runs live in memory and their sentences go out as toasts, so without this a run that stopped unwatched leaves nothing saying why. Bounded (one log, one record, logs kept), pruned oldest-first, and never a reason for a run to fail: an unwritable state directory is one warning and a nil handle every method is safe on.
- `hybridflow-runner/board_content.go` — the board as this service reads it: the cards, their settings, their chains — forgiving on the way in, narrow on the way out.
- `hybridflow-runner/chain_run_fault.go` — reading a reply as one of the CLI's error notices rather than as an answer, whether waiting is worth anything, and — for a usage limit, which says so — when it stops being true.
- `hybridflow-runner/flow_node_images.go` — the pictures a played flow node hands its turn: the markdown images and image links its body names, resolved from the store root into absolute paths the Read tool can take. They are files of the store rather than attachments, so nothing is copied and nothing is swept — see [PROTOCOL.md § Playing a board](/operation/worker/PROTOCOL/chain-runs.md).
- `hybridflow-runner/shutdown.go` — the machine's off switch: the configured command, or nothing at all, which is what says a board's Shutdown card cannot be honoured here.
- `hybridflow-runner/handlers_chain_run.go` — the six `/hybridflow-runner/chain-runs` handlers.
- `hybridflow-runner/handlers_conversations.go` — the six `/hybridflow-runner/conversations` handlers, the registry broadcasts that keep every tab's list live, and `conversationDto`: the join between what is on disk and whether a turn is running right now.
- `hybridflow-runner/claude_mcp.go` — the MCP configuration a turn is handed with `--mcp-config`. Two things: `BundledMCPServers`, what the staged kiao-mcp bundle offers this deployment (exported, because the program hands it to the toolbox), and the document itself, written **on the spawn path** rather than once at startup — named after the digest of its own contents, so an identical set of servers costs a stat and a set changed in the configuration panel reaches the next prompt. *Which* servers a turn gets is not decided here: the toolbox decides, through `MCPRegistry`. The credential those servers call back with is not in the document and is not here — it is `core/turntoken.go`, minted per turn, and only for a turn that actually got a kiao-mcp server.
- `hybridflow-runner/api.go` — `hybridflowrunner.Service`: the half assembled in the order its pieces depend on each other, and the turn-token registry it hands the program. `hybridflow-runner/routes.go` is its HTTP surface, as data.
- `hybridflow-runner/config.go` — the settings this half reads on top of the socle's: the Claude credentials, the login and bypass switches, the turn cap, the setting sources, the MCP bundle, whether Codex is offered and how strictly, the shutdown command.
- `hybridflow-runner/claude_usage.go` — `ClaudeUsageService` backing `/hybridflow-runner/usage`: probes the Anthropic API for `anthropic-ratelimit-unified-*` headers using the local Claude credentials.
- `hybridflow-runner/claude_options.go` — `ClaudeOptionsService` and the `/hybridflow-runner/options` payload: the curated model and permission-mode lists plus the efforts parsed from `claude --help`, cached for 10 min, so the client never hard-codes a list that drifts from the installed CLI. The endpoint answers **per agent** — the three lists once for each, the default agent's repeated at the top level so a client written before there was more than one keeps working.
- `hybridflow-runner/claude_login.go` — `ClaudeLoginService` backing `/hybridflow-runner/auth/*`: drives `claude auth login` on this host from a browser, parking one CLI process between the two round trips. Gated by `KIAO_WORKER_HYBRIDFLOW_RUNNER_CLAUDE_LOGIN_ENABLED`.
- `hybridflow-runner/muse_login.go` — `MuseLoginService` backing the Muse sign-in: the device flow (`POST /hybridflow-runner/auth/{agent}/login/*`, one parked `muse login` polled for the approval) and the one-round-trip API key (`POST /hybridflow-runner/auth/{agent}/key`, read off stdin). Gated by `KIAO_WORKER_HYBRIDFLOW_RUNNER_MUSE_LOGIN_ENABLED`.
- `hybridflow-runner/skills.go` — `syncSkills`, which installs the skills bundled into this binary (`reference/kiao-skills`) into the store at startup — `.agents/skills` for Codex, Muse and OpenCode, `.claude/skills` for Claude, which reads only that directory — so every way of starting KIAO gives a turn the same ones. **Which of them a store gets is its plugin list**: a skill is the agent half of a Dashboard plugin, and a store that has switched the plugin off cannot open the format the skill is about, so the skill is not installed and one already there is pruned. What that saves is a turn's attention rather than disk — a skill's description is read at the start of every turn. The list is `plugins` in the store's `dashboard.json`, read fresh at every pass, and every way of not answering it — no document, no key, unreadable — means every skill; an empty list is an answer and means none. The pass therefore runs at the save of that document as well as at startup, so switching a plugin takes effect on the next turn. Each installed skill carries a `.kiao-skill` marker recording two digests, because "up to date" is two questions: the bundled skill it was installed from (is this the right version?) and the tree as written (is it still what was written?). A directory with no marker was not written here and is reported rather than overwritten; one that answers both is left untouched; one that fails the first is updated and one that fails the second is restored, with a warning naming the source. A skill the store is no longer to have is removed, whether this build dropped it or the store switched its plugin off. The installed `SKILL.md` also ends with a comment naming `reference/kiao-skills/<name>/`, since that copy is the one a session finds when asked to change a skill and editing it achieves nothing. The same pass removes what the previous install wrote into the agent homes (`~/.claude/skills`, `~/.codex/skills`, `$XDG_CONFIG_HOME/muse/skills`), marker-gated so nothing else is touched. Never fatal — the turns lose their skills, the service does not lose its store.

**Migrations**

- `files/migrations.go` — versioned `V<NNN>__*.js` file-store migrations, run once in order via `node` and recorded in `<state>/files-migrations.json`. What a migration must leave alone is unenforceable from here — it is a Node script with full filesystem access — so the store's declaration is logged before the first script runs and honoured by the shared helpers the scripts use.
- `files/kiaofiles.go` — `.kiao-files`: a folder's declaration of what, in it and below, is not KIAO content. Parsing, matching, the scope a walk aimed at one folder carries (`kiaoScopeAt`, `kiaoWalk`), the defaults seeded into a new store, and the conversion of a legacy `<state>/migration-ignore`. Read by the link fixer, by search and the delete scope here, and by the migration helpers in Node.
- `files/configdocs.go` — `GET`/`PUT /config/{name}`: the Dashboard config documents, served from the state directory rather than the file store. A saved `dashboard.json` is announced (`OnDashboardConfigSaved`), because the plugin list in it is what decides the store's skills.
- `core/lock_linux.go` / `core/lock_other.go` — `core.AcquireLock`: advisory `flock` so only one instance migrates at a time, and — held for the whole process lifetime — so only one instance owns the state directory (best-effort no-op off Linux).

**Auth & process**

- `core/auth.go` — `Authenticator`: JWT validation (JWKS/RS256) in `prod`, decode-without-validate in `debug`; the auth middleware plus the redacted `core.Identity` used for logging, and `readerScope`, which is what the read-only `files_reader` role amounts to — the route allowlist the program hands it and the store prefixes it may be asked about.
- `core/proc.go` — `core.ProcResult` and the external-command runner shared by git, migrations, Claude and the toolbox.
- `core/mcp.go` — `core.MCPServer`, one entry of the configuration a turn is handed. In the socle for the reason `core.Route` is: the toolbox decides which servers a turn gets and the hybridflow-runner half decides how they are handed over, and between them there is only this shape.

**The toolbox (`internal/toolbox`)**
- `toolbox/pub.json` + `toolbox/catalog.go` — everything this service knows how to install: `pub.json` embedded in the binary, plus every `*.json` the deployment staged in `KIAO_WORKER_TOOLBOX_CATALOG_PATH`, merged after it in name order. One entry per component, with a **recipe per platform** (`generic`, `debian`, `alpine`) so one entry carries the three ways the same thing is obtained. A request names an id from this list and nothing else — no command, no package name, no version — which is the whole of what makes the surface safe to expose. Also the dependency closure, which is what turns "install fetch" into "install uv and fetch, is that alright?".
- `toolbox/install.go` — the channel drivers, and the one place in the worker that puts software on the machine. Every command is argv through `core.RunProc` and never a shell; every tool is pointed at the prefix so a global install lands there and not in `/usr` or in someone's home; every download is checked against a checksum the same server published. None of them asks for root: a JDK is a Temurin tarball, Node is the official LTS one, Python is uv's, ffmpeg is a release branch's static build from BtbN/FFmpeg-Builds, of which two files are taken out of the `.tar.xz`. The `system` channel is for the `kiao` image alone, where the process already is root and an install that skips `kiao-dev` does not survive the container being replaced.
- `toolbox/registry.go` — `<state>/toolbox.json`: what this service installed, and which servers are handed to a turn. It is the boundary of what the panel owns — an uninstall removes what this record names and nothing else, the same discipline as the `.kiao-skill` marker. Seeded once from `KIAO_WORKER_MCP_SERVERS`, and the authority from then on.
- `toolbox/probe.go` — the MCP handshake, run after an install. It answers two questions at once: did this actually start (a package that resolved and wrote its files can still fail to boot, and the only other place that shows up is a turn with quietly missing tools), and what will it cost — the tool count and the bytes of definitions every single request pays. Also `present`, which is how a runtime somebody else installed is told from one this service did.
- `toolbox/jobs.go` — an install is minutes, so it is a job, not a request held open: `POST` answers at once, the job appends to a log, the panel polls. One at a time, deliberately.
- `toolbox/platform.go` — which system this is, and therefore which recipes apply.
- `toolbox/api.go` — `toolbox.Service`: the panel (`State`), the two verbs, the registration toggle, and `MCPServers` — the port the hybridflow-runner half reads at every spawn. `toolbox/routes.go` is its HTTP surface, as data; `toolbox/handlers.go` the thin handlers; `toolbox/config.go` the two settings it reads, `KIAO_WORKER_TOOLBOX_PATH`, whose empty value makes the panel read-only, and `KIAO_WORKER_TOOLBOX_CATALOG_PATH`, whose empty value is the embedded `pub.json` alone.
