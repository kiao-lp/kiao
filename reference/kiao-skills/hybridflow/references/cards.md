# Cards — What a Card Says

Field semantics, transport-agnostic: the same whether the card is written with the
`kiao-hybridflow` MCP tools or over HTTP. For the transport itself — reaching the store,
the `curl` preamble, the recipes — see [api-curl.md](api-curl.md); for what happens after
a card — chains, shutdown, scheduler, gateway — see [chains.md](chains.md).

## The Card

Every field of a card, as it is on the wire. The names are the board's own.

| Field | Rule |
|-------|------|
| `id` | A UUID, **stable for the life of the card**. It is what a played turn is marked on. Minted by the service unless you send one. |
| `title` | What the card shows in bold. The card's **name** — read on the board, named by a chain — and the prompt where there is no description, never beside one. |
| `type` | **What kind of card it is**: `human`, `ai`, `shutdown`, `scheduler`, `gateway`, `note` or `value`. Always written out by the service; `human` is what a card created without one gets — see [Flow node Type](#flow-node-type). |
| `note` | Markdown on a **note** card, links included. That card's only content: no title, tags or status. |
| `value` | JSON payload on a **value** card, beside its `title`. The card shows a copy button for it. |
| `tags` | The words the card is filed under. **The words themselves**, never ids — see [Tags](#tags). |
| `body` | The **description**: what is sent when the flow node is played — or, where there is none, the title. Markdown, anything at all — headings included, at any level. A play leaves it where it is. A **task**'s alone: a Shutdown, a Scheduler and a Gateway have none, and one written on any of them is read back as nothing. |
| `criteria` | The **success criteria**: short pairs of autogenerated id and entered text saying what done means — `[{"id": "…", "text": "…"}]`. Sent with the prompt whenever present. A **task**'s alone, like the description. |
| `complexity` | How heavy the work looks, in Fibonacci points — `1`, `2`, `3`, `5`, `8`, `13`, `21`, or absent for none. Optional, and never sent anywhere. A **task**'s alone, like the description. |
| `settings` | What its turn is run with; see [Settings](#settings). Asked of an **AI** card, the folder alone of a **Human** one, and of none of the other three. |
| `at` | A **Scheduler**'s datetime — the local moment it waits for, as `YYYY-MM-DDTHH:mm`. Nothing on every other type — see [Waiting for an Hour](chains.md#waiting-for-an-hour). |
| `duration` | A **Scheduler**'s positive fixed wait from each play, such as `30s`, `15m` or `1h30m`. Alternative to `at`; setting one clears the other. |
| `spot` | Where the card sits on the board — `{ "x": …, "y": … }`, pixels from the top left of the canvas. Absent for a card nobody has placed — see [Where a Card Sits](#where-a-card-sits). |
| `status` | Where the flow node stands, in one of eight words; `ready` until something has had to say more — see [Status and Chat](#status-and-chat). |
| `chat` | The agent conversation the flow node is played in, by id. Empty until it has been played. |
| `onSuccess` | What is to be done after it: the card played next — or, on a Gateway, the branches started — the **transition mode**, and whether the chat is **compacted** — see [On Success](chains.md#on-success). |
| `run` | The run holding the card, or empty when it is free. Read-only; it is how a board knows not to offer a Play on a card somebody is already playing. |
| `classVersion` | The class version the card was made from — `{ "classId", "classTitle", "versionId", "versionNumber" }`. Read-only; patch `classVersion` with a version id to move it, `""` to break the link — see [classes.md](classes.md#binding-a-card-to-a-version). |
| `workflow` | The workflow the card is grouped in — a workflow of this board — or absent for none. Patch it to group the card, `""` to take it out. |
| `revision` | What to send back in `If-Match` to make the next write conditional — see [Writing](api-curl.md#writing). |

A card with no title, no description and no success criterion has nothing waiting to go out,
which is what it has to say: there is nothing to send.

## The Description

A **task** — an AI card or a Human one — has **a box to write in**: `body`, the **description**. What
is sent when the flow node is played, and the whole of it. A Shutdown, a Scheduler and a Gateway have
none: playing one *is* what it does, so there is nothing to ask of it. A play leaves it exactly where it is: what the turn said is in the
conversation the card names, which is the one record of it, and the card still asks what it was
asking — so a played card is played again as it stands, into the same chat.

- **The prompt is the description — or, where there is none, the title — and the success
  criteria, always, where there are any.** The title is sent only in place of a missing description,
  never beside one. A task is valid with a title, a description or a success criterion, so a flow
  node saying none of the three is **not played**: no Play on the card, and a chain reaching one ends
  there. Writing one of the three is what offers it a turn.
- **Every ending keeps the description.** Whatever the turn came back with — answered, stopped
  part-way, failed — the card is played again as it stands.
- **A chat outlives the description.** The card keeps naming the conversation, and the second
  description is played into it — which is what makes the second question worth asking there.

A **task** also says **what done means**: `criteria`, short pairs of autogenerated id and entered
text, added in its editing panel. Send both halves of each pair — mint an id where the criterion
has none — and send the list whole when it changes, like `tags`. They go out with the prompt as a
`Success criteria:` list, whatever else goes out with them, so a turn always knows what it is
measured against.

And it says **how heavy it looks**: `complexity`, one of `1`, `2`, `3`, `5`, `8`, `13`, `21`, or
absent for none. Optional, and never sent anywhere. Both are the task's own: written on a Shutdown
or a Scheduler, either is read back as nothing.

**A body may carry images**, and they are files of the store the markdown links. **Write those links
from the store root, with a leading slash** — `![shot](/boards/major/shot.png)` — because a card has
no folder of its own to read a relative link against. Pasting a screenshot into the editor writes
the file into the board's folder and the link with it. When the flow node is played, the turn is
told where each of those files is so it can read them, so a flow node about a screen should show the
screen rather than describe it.

## Where a Card Sits

A board is one canvas: every card sits where somebody put it, and an arrow is drawn from each card
to the one it hands on to. Each card carries its place: `"spot": { "x": 320, "y": 160 }`.

- **Pixels, from the top left of the canvas**, and never negative. Whole numbers.
- **Absent means never placed.** The editor places such a card the first time it draws it — a row
  per chain, left to right along it — and writes the place down then. **You do not need to send one.**
- **Do not copy one between boards.** A place is a place on *that* canvas among *those* cards, so the
  same point on another board is a card on top of whatever is already there.
- **Where you do send one**, keep the cards a card's width apart — about `260` across and `160` down
  is what the editor's own layout uses — or they overlap. `"clearSpot": true` takes a card off the
  board again.
- **Moving a card is patching its `spot`.** There is nothing else a place is: no filing, no order,
  no rank.

## Tags

A card may carry the words it is filed under: `"tags": ["bug", "ui"]`.

- **A tag is the word.** There are no ids here and nothing to look up: write the word the user says.
  The store keeps a colour for each known word in `kiao-user-config/tags.json`, and that file is the
  *only* thing it keeps — a word it has never named is still worn on the card, in a neutral grey.
- **It is not a status or a setting.** Tags say what a card is *about*. Nothing about a
  tag says what runs the flow node, so it never goes in `settings`.
- **Case and spacing.** A word is trimmed and its inner whitespace collapsed, and a card cannot wear
  the same word twice — `bug` and `BUG` are one tag. Match the spelling the store already uses when
  there is one.
- **Adding a word the store does not know is fine.** It appears in grey until somebody colours it in
  the Tags panel. Do not edit `kiao-user-config/tags.json` unless the user asks.
- **`tags` is a whole replacement**, like `settings`: send the list the card is to wear, not the one
  word being added. Read the card first.

## Status and Chat

Two fields a **play** writes onto a flow node, and which the board's panel can also be used to write.

| Value of `status` | Meaning |
|-------|---------|
| `draft` | Still being written, and not to be played until it is. |
| `ready` | Waiting to be played. What a card says until something has had to say more about it. |
| `blocked` | Waiting on something that is not on the board: an answer somebody owes, a deploy that has to land first, a decision nobody has taken. The card is written and would play as it stands; what holds it up is outside. The user's word — no play writes it and none clears it. |
| `running` | A play has it: the turn was sent and nothing has come back yet. Written before the prompt goes out, so a board read anywhere says which flow node is being worked on. |
| `waiting-refresh` | A play has it and can do nothing with it: the agent's usage limit was reached mid-turn, and the run is holding the flow node until that limit lifts. It goes back to `running` when the run picks the turn back up. |
| `interrupted` | Its turn was stopped part-way. What it said before the stop is in the conversation, and the flow node was not finished. |
| `done` | Its turn came back an answer, which is in the conversation — and the description it sent stays where it is. |
| `error` | Its turn came back an error, or never ran. **Its description is kept**, so the card is played again as it stands. |

**Only a `ready` flow node is played** — every other card carries no Play, and the way to offer a
flow node a second turn is to set it `ready` again.

**Never write `running` or `waiting-refresh` by hand.** Those two say a run is holding the card, and
a card left saying so with no run behind it is a card nobody can play and nothing will free.
`blocked` is the opposite case and is yours to write: nothing is holding the card, which is why it
waits, and nothing but a patch back to `ready` will free it.

`chat` is the conversation the flow node is played in. A flow node played without one gets a
conversation made for it and the id written onto it at once; a flow node played **with** one is
played into it, however it came by it — its own last play, or the flow node before it in a chain.
**Do not write a `chat` by hand**: an id that names no conversation is a flow node that will fail to
play, and an id copied from another flow node is two cards claiming one transcript.

A played flow node **does not move**. The status says it has been played, and the card stays
where it was put.

## Flow node Type

**Every card is one of seven kinds**, and the editor asks it first, above everything else on the card:

| Type | What it is | How the card says it |
|------|-----------|--------------------------|
| **Human** | A card somebody works through themselves. | `"type": "human"` — what a card created saying nothing is given. |
| **AI** | A card an agent plays. | `"type": "ai"`, and a `settings` beside it. |
| **Shutdown** | Playing it turns the machine off, and the play ends there. | `"type": "shutdown"`, and **nothing else on the card** — see [Shutting the Machine Down](chains.md#shutting-the-machine-down). |
| **Scheduler** | Playing it waits for a datetime, then plays the flow node after it. | `"type": "scheduler"`, with an `"at"` — see [Waiting for an Hour](chains.md#waiting-for-an-hour). |
| **Parallel gateway** | Playing it waits for every branch feeding into it, then starts every branch leaving it, in parallel. | `"type": "gateway"`, with a list of branches — see [Joining and Forking](chains.md#joining-and-forking). |
| **Note** | Markdown shown on the board. Never played, never chained. | `"type": "note"`, with `note` alone. |
| **Value** | A title and a JSON payload shown on the board, with a copy button. Never played, never chained. | `"type": "value"`, with `title` and `value`. |

**The first two are tasks, and that is the word to use for them.** A **task** is a flow node that is
work somebody does — an AI card an agent plays or a Human card a person does. The other three are the
board acting on its own machine and describe no work, which is why they are asked for neither a
`body` nor a `folder`. Say *task* when you mean the pair; say *flow node* when you mean any card on
the board. The store keeps the pair's own fields in a `task` table of its own, but the wire is flat
and a card is read here exactly as the table above says.

**Write the type.** A card created with none and a `settings.agent` is read as AI, and one with
neither as Human — that forgiveness is for boards written before the field existed, not a licence to
leave it out. A card you mean to be a Shutdown, a Scheduler or a Gateway must say so.

**Keep the type and the settings in step.** `"type": "ai"` with no `agent` is a card claiming to be
played by nothing, and `"type": "shutdown"` beside an `agent` is a card saying two things.

What each is asked, and what is simply not put to it:

| | Human | AI | Shutdown | Scheduler | Gateway |
|--|--|--|--|--|--|
| a **task** | yes | yes | **no** | **no** | **no** |
| `title`, `tags`, `status`, `spot` | yes | yes | yes | yes | yes |
| `body` — the description | yes | yes | **no** | **no** | **no** |
| `criteria` — what done means | yes | yes | **no** | **no** | **no** |
| `complexity` — how heavy it looks | yes, optional | yes, optional | **no** | **no** | **no** |
| `settings.folder` | yes — where the work is is worth writing down whoever does it | yes, and **required** | **no** | **no** | **no** |
| `onSuccess.flowNode` — the flow node that comes next | yes | yes | **no** | yes | **no** |
| `onSuccess.flowNodes` — the branches that come next | **no** | **no** | **no** | **no** | yes |
| `settings.agent`, `effort`, `permission` | **no** | yes, all three required | **no** | **no** | **no** |
| `settings.runner` — which runner plays it | **no** | yes, optional | **no** | **no** | **no** |
| `chat` | **no** | yes, written by the play | **no** | **no** | **no** |
| `onSuccess.mode` — the transition mode | **no** | yes | **no** | **no** | **no** |
| `onSuccess.compact` — the chat shortened at the end | **no** | yes | **no** | **no** | **no** |
| `at` — the datetime | **no** | **no** | **no** | yes, and **required** | **no** |

The rows saying **no** are the ones to watch: what a type is not asked is **read back as nothing**,
so a `mode` other than `end` on any card but an AI one is read as `end`, a `compact` there is read
as false, a `flowNode` named after a Shutdown is read as none, a single `flowNode` named on a Gateway
is read as none — its branches are the list beside it — and a `body`, `criteria`,
`complexity` or `settings` written onto a Shutdown, a Scheduler or a Gateway is dropped — a card that
is no task has nothing for any of them to be kept on. A field nothing shows and nothing
can reach would sit in the database marking the card as broken with no control to fix it on.

## Agents

An **agent** is a named definition of what plays a flow node: which engine runs the turn, on which
model, under which standing instructions, and when to choose it for a task. It is what a flow node's
`settings.agent` names — the id, never the engine — so renaming the model a team plays on is one edit
here rather than one edit per card. They are kept in the Flow node agents panel, and behind the API
beside the boards.

Over MCP these are the `agent_*` tools; without them, the same calls over HTTP — with the
preamble from [api-curl.md](api-curl.md#reaching-the-boards):

```bash
curl -sS -H "$AUTH" "$HYBRIDFLOW/agents"                                  # every agent, by name
curl -sS -H "$AUTH" "$HYBRIDFLOW/agents/<id>"                             # one agent
curl -sS -X POST "$HYBRIDFLOW/agents" -H "$AUTH" -H "$ACTOR" \
     -H 'Content-Type: application/json' \
     -d '{"name":"Reviewer","platform":"claude","model":"opus","description":"Reviews code for correctness.","instructions":"Be concise."}'
curl -sS -X PATCH "$HYBRIDFLOW/agents/<id>" -H "$AUTH" -H "$ACTOR" \
     -H 'Content-Type: application/json' -H "If-Match: 1" -d '{"model":"sonnet"}'
curl -sS -X DELETE "$HYBRIDFLOW/agents/<id>" -H "$AUTH" -H "$ACTOR"        # 204
```

| Field | Rule |
|-------|------|
| `id` | Minted by the service. Never sent on a create, and what flow nodes name. |
| `name` | What the flow node editor shows. Unique across the store, however it is cased. |
| `platform` | `claude`, `codex`, `muse` or `opencode`. Nothing else is one. |
| `model` | The model the agent runs on, or empty for the CLI's own default. |
| `description` | When to choose this agent for a task. Selection guidance, never sent to the agent's turns; empty clears it on a patch. |
| `instructions` | Standing orders its turns are given, beside the prompt. Empty for most agents. |

**Read the agents before naming one, and read their descriptions before picking one.** A card's
`agent` is an id, and a card naming one nothing holds is refused at the write — match it against
the listing rather than guessing it. Keep the selection guidance separate from `instructions`:
descriptions are never sent to the agent's turns. **Ask before deleting one**: the flow nodes
naming it keep naming it, and cannot be played until they name another.

## Runners

A **runner** is a machine that plays cards — and `settings.runner` is the card saying which one
plays it. A card naming none is played wherever a Play is pressed; a card naming one waits for
that machine.

Over MCP these are the `runner_*` tools; without them, the same calls over HTTP — with the
preamble from [api-curl.md](api-curl.md#reaching-the-boards):

```bash
curl -sS -H "$AUTH" "$HYBRIDFLOW/runners"                                  # every runner
curl -sS -H "$AUTH" "$HYBRIDFLOW/runners/<id>"                            # one runner
curl -sS -X POST "$HYBRIDFLOW/runners" -H "$AUTH" -H "$ACTOR" \
     -H 'Content-Type: application/json' -d '{"name":"local"}'
curl -sS -X PATCH "$HYBRIDFLOW/runners/<id>" -H "$AUTH" -H "$ACTOR" \
     -H 'Content-Type: application/json' -H "If-Match: 1" -d '{"name":"remote"}'
curl -sS -X DELETE "$HYBRIDFLOW/runners/<id>" -H "$AUTH" -H "$ACTOR"       # 204
```

| Field | Rule |
|-------|------|
| `id` | Minted by the service. Never sent on a create, and what cards name. |
| `name` | What the task editor shows. |
| `lastSeen` | When the runner last said it was alive — or absent for one that never has. Read-only. |

**Read the runners before naming one**, like the agents: a card's `runner` is an id, and one
nothing holds is refused at the write.

## Settings

The fields that say what a turn is run with. Not sent at all for every card but an AI one, whose
`folder` a Human card is asked for too:

```json
"settings": {
  "agent": "3fa85f64-…", "effort": "high", "permission": "manualLive", "folder": "/"
}
```

| Key | Meaning | Default |
|-----|---------|---------|
| `agent` | Which agent plays the flow node — a managed agent's **id** (see [Agents](#agents)). | **None.** Required. |
| `effort` | How hard it thinks. | None, and required alongside `agent`. |
| `permission` | How its tool calls are answered — one the agent's **platform** offers. | None, and required alongside `agent`. |
| `folder` | The folder the turn runs in, written as a **link**: from the store root, with a leading slash — `/exchange/dashboard`, and a lone `/` for the store root itself. A flow node played in a chat it already has runs in **that conversation's** folder. | None. Required alongside `agent`, and asked of a Human flow node all the same. |
| `runner` | Which runner plays the card — a runner's **id** (see [Runners](#runners)). | Absent: wherever a Play is pressed. |

**`settings` is a whole replacement, not a patch.** The keys are a set a form submits together, and
patching one of them alone would make "no effort" and "unchanged effort" the same request. Read the
card, change the one key, send them all back.

**`agent` comes first, and the two beside it depend on it.** The effort and the permission mode are
vocabulary of the platform the agent runs on: Codex has no `manual` — it never asks, so the mode
does not exist for it — and OpenCode is the same, for the same reason. Write the two to match
the platform, or the card is refused at the click with a message naming both. A card naming
an agent whose platform the deployment does not offer is refused the same way, which is what
happens to a board written on one machine and played on another.

A card written before managed agents names the engine itself, with the model beside it —
`"agent": "claude", "model": "opus"`. Those cards are played as they always were; `model` is read
and never written, so leave it out of anything new and let it fade where a card's settings are next
written.

Nothing here says what **kind** of card it is — that is `type` — nor what happens **after** the flow
node, which is `onSuccess`.

Typical values, though each platform's own lists are authoritative:

- `effort`: `low`, `medium`, `high`, `xhigh`, `max`
- `permission`: `manual`, `manualLive`, `bypassPermissions` — but `bypassPermissions` alone on `codex` and `opencode`

**An AI flow node is played only when it names all four.** None of them falls back to whatever the
deployment happens to run: a played turn is one nobody is sitting at, so which agent runs it, what
it costs, what it may do on its own and where it writes are things the user chose. A flow node
missing any of them is not played, and its card says which is missing.

## Copy and Paste

Flow nodes are copied to the system clipboard as JSON, from the board's right-click
menus, and pasted back — including **into another instance of KIAO**, which is what the feature is
for.

```json
{ "kind": "kiao-flow-node",  "version": 1, "flowNode":  { "id": "…", "title": "…", "body": "…" } }
{ "kind": "kiao-flow-nodes", "version": 1, "flowNodes": [ { "id": "…", "title": "…" } ] }
```

One card is written under the singular wrapper and several under the plural one. A bare flow node
object and a bare JSON *array* of flow node objects are accepted too, so JSON written by hand or by
a turn can be pasted straight onto a board. A copy wrapped the old way — `kiao-workflow-flow-node`
— pastes as it always did. **A paste always mints new ids.** A **chain travels with
whatever carries both its ends** — the cards copied together — so those `onSuccess` links are
rewritten with the ids their flow nodes are given.

A `status` travels — it is what the flow node says about itself. A `chat` never does: it
names a conversation of the instance it was copied from. The `criteria` and the `complexity`
travel, like the description: they are the task's own words about its work.

Handing the user a block of this JSON to paste is a reasonable way to offer several cards at once
when you would rather they chose where the cards land. Creating them with one call is the other.

## Flow node Templates

A flow node's description is written **from a template** in the boards editor: the `.temp.md` files a
store keeps in **`kiao-user-config/flow-node-templates`**. They are ordinary template-lang templates —
see the `template-lang` skill — in a flat folder of their own. Both faces of the editor carry a select of
them and a button that instantiates the one it names; instantiating **replaces** the description
with the result.

Two of them have names the board knows, `AI.temp.md` and `Human.temp.md`, and typing a card picks
the one that goes with its type. Where the store has neither, they are written the first time a
board is opened: `AI` carries the standing instructions a played turn is given — be concise, work at
the strategic level, commit but do not push — around `${flowNodeDescription}`, and `Human` is
`${flowNodeDescription}` alone.

Two variables the flow node answers itself: **`${flowNodeDescription}`** is what the card says now,
so a template writes *around* the description rather than replacing what is in it, and
**`${flowNodeTitle}`** is its title.

**Nothing outside the editor instantiates anything.** A card you create over the API carries exactly
the body you sent, and what a play sends is the description as it stands. If the card is meant to
read like the ones the editor makes, read `kiao-user-config/flow-node-templates/AI.temp.md` and
write its standing instructions into the body yourself.

## Common Mistakes to Avoid

- **Writing a `.workflow.json` file.** Nothing reads one, anywhere — not the editor, not the
  runner, not the store. The board the user is looking at lives behind the API, and a file beside
  it is a second version of the truth that will never be seen.
- **Editing a board without reading it first.** Card ids, spots and revisions all come from the
  read, and a write that guessed one of them does nothing or does it somewhere else.
- **Patching `settings` or `tags` with one key.** Both are whole replacements: the other keys are
  not kept, they are cleared.
- **Writing `running` or `waiting-refresh`**, or calling `/play`, `/played` or `/settle`. Those say
  a run holds the card. A card left saying so with no run behind it is stuck.
- **Writing a `chat` id.** It names a conversation of the instance that made it; a card pointing at
  one that does not exist fails at its first play.
- **Reusing a card id.** Ids are the card's identity across every board; send none and let the
  service mint one unless you are pasting something that already had one.
- **Changing a card's id when moving it.** A move is a move; the id is what makes it the same card.
- **Leaving the type off a Shutdown, a Scheduler or a Gateway.** Those three are nothing but
  their type: a card without it is a Human card with a title.
- **A `type` and settings that disagree.** `"type": "ai"` with no `agent` is a card claiming to be
  played by nothing; `"type": "shutdown"` beside an `agent` is a card saying two things.
- **Naming an agent but no effort, no permission or no folder** — the flow node is not played,
  and nothing on the board fills the missing field in for you.
- **Naming an agent id nothing holds.** Read the agents first; a guess is refused at the write.
- **Naming a runner id nothing holds.** Read the runners first, like the agents.
- **Writing a `model` on a new card.** The engine and the model are its agent's to say; `model` is
  what a card written before managed agents says, and it fades where the settings are next written.
- **A `chat`, a `mode` other than `end`, or a `compact` on a card that is not AI.** None of them
  means anything where there is no conversation.
- **A `body`, `criteria`, `complexity` or `settings` on a Shutdown, a Scheduler or a Gateway.**
  None is a task, so none has anywhere for one to be kept: what you send is dropped, and a patch that
  asked for nothing else is refused.
- **Something said about the chat with nothing to play the flow node.** `continue` and `compact`
  both say the flow node is an agent's; on a flow node whose `settings` do not name all four, the
  card is invalid and nothing runs.
- **Chaining a Shutdown to something.** The play ends there, so anything named after it goes
  unplayed. It is the last card, always.
- **A Scheduler with neither `at` nor `duration`, or both nonempty.** Choose a positive duration or a local datetime without a zone.
- **A single `flowNode` on a Gateway, or `flowNodes` anywhere else.** A Gateway names its branches
  the list way and one card follows every other kind: each written on the wrong kind is read as
  nothing.
- **Redrawing a Gateway's chain to move a branch.** The link call **adds** a branch to a Gateway;
  taking one off is the panel's multi-select, or a patch naming the list without it.
- **Filing a Gateway as a class.** A class is reusable words and a Gateway holds none: the write is
  refused.
- **Chaining across folders.** Where the chat is carried on, every flow node of a chain runs in the
  conversation's folder: a chained flow node naming another stops the play.
- **Chaining a card to itself, or round in a circle.** The play notices and ends the chain, but the
  board is saying something it does not mean.
- **Writing a tag as an id, or as an object.** `tags` is an array of plain words.
- **A relative image link in a body.** A card has no folder to read it against. Write
  `/boards/<handle>/shot.png`.
- **Grouping a card of another board.** A workflow holds cards of its own board, and a member
  from elsewhere refuses the whole call.
- **Mixing the two halves.** A workflow holds flow nodes and a workflow class holds classes;
  there is no call that puts one in the other.
